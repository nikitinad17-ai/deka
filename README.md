# Дека 2 · 0.1.0

Отдельное приложение на основе проверочной Деки 0.9.0, а не обновление Деки 1.
Android applicationId: `ru.deka2.player`. Название на устройстве: `Deka 2`.
Windows: отдельные `Deka2.exe`, `Deka2-setup.exe`, каталог и идентификатор установки.
Исходники развиваются в ветке `deka2`; `main` и релизы первой Деки не изменяются.

## Возможности

Горизонтальный режим: две деки A/B, независимые списки и поиск, микшер посередине.
Два локальных файла воспроизводятся независимо: CUE, EQ, уровни, кроссфейдер.
VK остаётся одним общим потоком. Две песни VK одновременно не сводятся.
Библиотека накапливается по идентификаторам; неполный проход не удаляет сохранённый хвост.
Сохранены явный прогресс, отмена загрузки, виртуальные списки и фоновые Android-компоненты.
Одинаковый двухдековый интерфейс используется на Android и Windows.

## Установка

`Deka2.apk` устанавливается рядом с первой Декой и Deka Preview.
Удалять старую Деку не нужно. В VK нужно войти заново: сессии и данные приложений изолированы.
Старые плейлисты не переносятся автоматически. Первая установка называется «Установить»,
следующие совместимые выпуски Деки 2 можно будет ставить как «Обновить» с тем же ключом.
Windows: запустить `Deka2-setup.exe` или отдельный `Deka2.exe`.

## Сборка и проверки

`npm install`, затем `npm test`, `npm run dev` либо `npm run build`.
`npm run prepare:brand` идемпотентно применяет имя и префикс `deka2:` к унаследованным
исходникам и тестовым фикстурам. Выполняется автоматически перед test/dev/build,
и явно перед `tauri android init` в CI. Движки, VK-доступ и алгоритмы тестов не подменяются.
Браузерные тесты: `pip install -r tests/requirements.txt`,
`python -m playwright install chromium`, `python tests/browser.py`.
Тесты синтетические: 1500 треков в модульном тесте и 1000 в браузере.
Живая VK-сессия пользователя и физическое выключение экрана не проверялись.

## Отдельная подпись Android

Используются только `DEKA2_KEYSTORE_BASE64`, `DEKA2_KEY_ALIAS`, `DEKA2_KEYSTORE_PASSWORD`.
Ключи первой Деки из истории Git не извлекаются.
Для первого выпуска CI генерирует новый ключ и шифрует его вместе с паролем
для публичного ключа владельца из `keys/deka2-recovery-public.pem`.
`Deka2-signing-backup.sealed.json` можно хранить публично: это AES-GCM/RSA-OAEP конверт,
не открытый keystore. Секретный recovery-ключ передаётся владельцу отдельно, не через GitHub.
После публикации первого выпуска генерация другого ключа запрещена: для дальнейших
сборок необходимо восстановить текущий ключ и настроить три DEKA2 GitHub Secrets.
Смена ключа без плана миграции не допускается.

Восстановление на личном компьютере:

```sh
python -m pip install cryptography
python scripts/signing-envelope.py recover Deka2-recovery-private.pem Deka2-signing-backup.sealed.json private-signing
```

Не коммитить `private-signing` и секретный recovery-ключ. Приватную копию хранить надёжно.
